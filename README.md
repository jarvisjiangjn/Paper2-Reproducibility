# Paper 2: Permission-Aware SQL Revision for Text-to-SQL Data Agents

This repository contains the research prototype and released D1 results for the Paper 2 experiments on bounded, permission-aware SQL revision. The implementation evaluates a generated SQL proposal against a column-level access policy, attempts a bounded revision when configured, and applies deterministic authorization and dependency checks to the candidate.

> **Scope of the results.** The D1 input consists of benchmark query-policy records whose reference SQL is used as the initial proposal. It is not a collection of SQL statements generated by deployed data agents. Passing the authorization gate or executing successfully does not establish semantic equivalence or answer sufficiency.

## Contents

- `run_unified.py` — unified D1/D3 experiment entry point.
- `engine/` — OpenAI-compatible API request helper, bounded revision methods, authorization gate, and dependency audit.
- `verify_sqlite.py` — post-hoc read-only SQLite execution audit.
- `preflight_spider.py` — checks whether the SQLite databases required by D1 are available.
- `scripts/download_access_control_dataset.py` — downloads and validates the Spider access-control input used by the released D1 outputs.
- `scripts/install_spider_database.py` — installs SQLite database files from a locally downloaded Spider archive.
- `frozen_scenarios.jsonl` — frozen synthetic recovery scenarios for D3.
- `baseline_results/D1/` — released offline `deny_only` and `rule` results.
- `results/D1/` — released results for the three LLM revision methods and SQLite execution audit.
- `config.example.json` — example model configuration without credentials.

Downloaded datasets and local credentials are deliberately excluded from the repository.

## Requirements

- Windows 10/11 is supported by `run_windows.bat`; command-line instructions also work on other operating systems.
- Python 3.10 or newer.
- The core experiment scripts use only the Python standard library; no `pip install` step is required.
- LLM revision methods require an API endpoint compatible with the OpenAI Chat Completions API and a valid API key.

## 1. Get the data

### 1.1 Spider access-control records (required for D1)

Run:

```powershell
python scripts/download_access_control_dataset.py
```

The script downloads `spider-access-control.zip` from the official [LLM-Access-Control-Datasets repository](https://github.com/klisura-code/LLM-Access-Control-Datasets), extracts `spider-access-control.jsonl`, validates the required fields and 19,624-record count, and installs it as `data/access_control_dataset.jsonl`.

The script also checks the SHA-256 of the exact D1 input used to produce the released results. If the upstream file changes, the script stops rather than silently mixing a different dataset with the released results. To intentionally use a changed upstream revision, pass `--force --allow-updated-source`; then run into a **new output directory** and do not compare its manifest as if it were the released input.

Official source and citation:

- Dataset: [Klisura et al., *Role-Conditioned Refusals: Evaluating Access Control Reasoning in Large Language Models*](https://aclanthology.org/2026.findings-eacl.316/).
- Source repository: [klisura-code/LLM-Access-Control-Datasets](https://github.com/klisura-code/LLM-Access-Control-Datasets).

### 1.2 Spider SQLite databases (required for SQLite execution audit)

The D1 authorization/revision experiment can run without local SQLite database files. The post-hoc execution audit requires them.

1. Download the official Spider 1.0 archive from the [Spider project page](https://yale-lily.github.io/spider). The project page identifies the dataset as distributed under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/).
2. Keep the downloaded ZIP outside this repository if you prefer not to store the large archive in the project folder.
3. Install only the SQLite databases and `tables.json` into the expected layout:

```powershell
python scripts/install_spider_database.py --archive "C:\path\to\spider.zip"
```

The resulting database layout is `data/spider/database/<db_id>/<db_id>.sqlite`. The installer does not unpack unrelated archive files. If the databases are already installed, use `--overwrite` only when you intend to replace them.

### 1.3 Check the local data

After the access-control JSONL and Spider SQLite files are in place, run:

```powershell
python preflight_spider.py
```

The preflight summary is written to `results/spider_preflight.json`. It lists any missing or unreadable databases rather than silently skipping them.

## 2. Configure model access

Copy the example configuration to a local-only file:

```powershell
Copy-Item config.example.json config.json
```

Edit `config.json` only if you need to change the provider URL, model identifier, timeout, or retry count. Set the API key in the current PowerShell session:

```powershell
$env:PAPER2_API_KEY = "YOUR_API_KEY"
```

Never commit `config.json`, `.env`, or an API key. The repository's `.gitignore` excludes local configuration and downloaded datasets.

## 3. Run the experiments

### 3.1 Offline D1 baselines

```powershell
python run_unified.py --dataset D1 --methods deny_only rule --out reproduced_results/baseline
```

### 3.2 API pilot (first 20 records)

```powershell
python run_unified.py --dataset D1 --methods naive_retry sql_aware_retry diagnostic_revision --max-cases 20 --enable-api --out reproduced_results/pilot
```

Review the API configuration and potential cost before starting a full run.

### 3.3 Full D1 LLM experiment

```powershell
python run_unified.py --dataset D1 --methods naive_retry sql_aware_retry diagnostic_revision --enable-api --out reproduced_results/D1
```

The runner writes JSONL outputs, a manifest, and `summary.json`. The manifest records the input hash, method list, model identifier, and protocol settings. Reusing an output directory with a different manifest is rejected. For a new model or changed dataset, use a new output directory.

### 3.4 D3 frozen-scenario experiment

```powershell
python run_unified.py --dataset D3 --methods deny_only rule naive_retry sql_aware_retry diagnostic_revision --enable-api --out reproduced_results/D3
```

This command runs all rows currently present in `frozen_scenarios.jsonl`. **The supplied file currently contains 88 rows: 44 transport scenarios and 44 energy scenarios.** Reconcile this count with the manuscript's D3 sample description before treating these outputs as the exact results reported in the paper.

### 3.5 SQLite execution audit

After a D1 run, execute:

```powershell
python verify_sqlite.py --results reproduced_results/D1 --out reproduced_results/D1/execution_audit.csv
```

The audit only executes candidates that pass both the authorization gate and dependency audit, using read-only SQLite connections and query limits. By default, the CSV omits the benchmark question/reference SQL and raw result-row samples. Join the output to the downloaded D1 input by `scenario_id` when you need the original context. Use `--include-context` or `--include-samples` only for local review; avoid publishing the expanded output unless it is necessary and consistent with the dataset terms.

`executed` means the SQL ran successfully under this SQLite setup. It does **not** mean the candidate is semantically equivalent to the original request.

## 4. Released results

The repository retains the D1 baseline JSONL files, the three D1 LLM result files, their manifests and summary, and the execution-audit CSV. The released execution-audit CSV omits raw result-row samples and duplicated benchmark question/reference SQL text; this does not change the execution status counts or query-output hashes. The original context can be joined from the downloaded D1 input using `scenario_id`. Some result records retain candidate SQL that is identical to the benchmark reference SQL for initially permitted cases; follow the source dataset's terms and cite the upstream datasets when redistributing or reusing those records.

The supplied archive did not contain D3 result files or the separate manual semantic-audit spreadsheet. The frozen D3 scenarios are included, but the D3 results and human semantic labels must be added only after the manuscript's sample count and the exact audit version have been reconciled. See [`docs/PREPUBLICATION_CHECKLIST.md`](docs/PREPUBLICATION_CHECKLIST.md).

## 5. Interpretation and limitations

- The authorization gate uses SQLite compilation/authorizer behavior as a supported-dialect check. It is not a PostgreSQL-native authorization proof.
- D1 uses benchmark reference SQL as initial proposals; it does not estimate real-world Text-to-SQL agent failure rates.
- Authorization acceptance, SQL execution, and semantic sufficiency are different outcomes. The code marks semantic status as unverified unless a separate human audit is performed.
- The D3 scenarios are synthetic, frozen cases. Their results should be reported separately from D1 benchmark results.
- API calls can incur provider charges and may change if the model or endpoint changes.
